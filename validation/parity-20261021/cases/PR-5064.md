## Pinned upstream reproduction and regression specification

The following is source material from the approved PR, not a record of testing this combined build. Test the stated scenario, values and regression names in addition to the procedure above.

The performance section explained how to run the whole benchmark, how to add a scenario and what CI
does — but not how to measure **one** scenario, nor the traps in reading the numbers. This adds both
to `docs/development.md` §"Scorecard and performance budgets":

- `xtask perf`'s exact flags, and the fact that it has **no `--only`**: to time one row you run the
  bench binary itself (`--only` matches row names with `contains`, plus `--group` and `--reps`),
  which writes its own report and does **not** evaluate budgets.
- `--reps` defaults to 7 in `--quick` and 15 otherwise, is per bench, and some rows cap it
  themselves (the `#211` algorithm rows use `b.reps.min(5)`). Percentiles are nearest-rank, so
  **at n ≤ 5 the "p95" is simply the maximum**.
- A budgeted scenario the baseline has no row for **fails** the run (`missing` is in
  `Status::fails()`), so the `[[scenario]]` and its baseline row belong together.
- A red `cargo xtask perf` is not necessarily your budget: the committed baseline carries
  `failed.P12` (a wgpu panic writing `pc_compose_uniforms`).
- The committed baseline was written on 2026-10-05 at a load average near 225 on a 14-core M4 Pro,
  which is why P26/P27 read as over budget there while `perf/budgets.toml` records 20–45 ms p95 for
  P26 on a clean 16-core machine.
- What flipping `enforce` commits you to, and why the flip and the baseline refresh belong in one
  change on the nightly's own machine class.
