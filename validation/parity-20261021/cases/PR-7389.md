## Root cause, as far as the code shows it

A recorded step is stored as raw command params, and `image.adjustments.photoFilter` accepts preset-only params (`{"filter": "cooling80", "density": 60}` — no `color` key; `crates/engine/src/adjust_params.rs` resolves the preset through `PHOTO_FILTERS` at run time). The `.atn` exporter built its descriptor straight from those params (`adj_fields!("PhtF", …, F("Clr ", "color", …))`), so a preset-only step exported **with no `Clr ` at all**: the export succeeded (a valid descriptor), the preset was gone, and re-imported playback fell back to the default warming filter — that is the issue's "accepted and lose their preset; imported playback uses the default warming filter".

The honest caveat the fix carries: Photoshop's own descriptor keeps no preset key for Photo Filter. That is what this repository's `phfl` notes conclude from the Photoshop CS2 oracle files (#3777/#4940, `crates/io/src/adjust_map.rs`: "the Yellow filter holds (24191, 25002, 3827) … Warming Filter (85) holds (15548, 12029, 0)"), and it is what the existing `.atn` event table shows (colour, density, preserve-luminosity, nothing else). So "keep the preset" can only mean "export the resolved colour", which keeps the output identical.

## What

`crates/engine/src/atn_cmds.rs`, the `PhtF` entry of `ADJUSTMENTS`:

- a preset-only step now exports its resolved colour (`preset_color` looks the id up in the same `adjust_params::PHOTO_FILTERS` table the command itself uses, so the export matches what running the step in PhotoCraft produces);
- an explicit `color` keeps precedence over `filter`, exactly like running the command;
- an unknown preset id keeps the previous export (no colour) — export still never rejects a step;
- density stays implicit when the step had none (playback then applies the same default both for the original preset-only step and for the re-imported one).

Import is unchanged: neither direction can recover a preset name, and none is invented.
