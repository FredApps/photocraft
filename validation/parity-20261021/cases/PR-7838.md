## Pinned upstream reproduction and regression specification

The following is source material from the approved PR, not a record of testing this combined build. Test the stated scenario, values and regression names in addition to the procedure above.

Part of #7807 (the 2³⁰ px cap). Builds on #7837 (its first two commits); the last three commits are this PR. #7839 makes the error text copyable.

A transform's result was capped at 2³⁰ px, so a stitched layer past about 1 GP couldn't be transformed on any machine. Three changes:

- The warp writes each tile into the result as soon as it is warped. Before, every finished tile kept its `f32` pixels until the last one was done: 16 bytes a pixel of an RGBA result on top of the result itself.
- The result is priced in bytes at its pixel format (with the alpha the warp adds) against Preferences › Performance › Memory Usage (default 8192 MB), which `Session::apply_prefs` now passes to the engine, as it does the effect-cache budget. Past it, the message names the setting: "… would be 37708 x 35259 px (10144 MB), more than the 8192 MB Memory Usage allows (Preferences › Performance) …".
- A result the warp would clip is refused. The warp places pixels within ±2²⁰ px and clamps the rest away, so a wide strip could fit the budget and lose its end; a plain move past ±2²⁰ px already emptied the layer silently on main. It now says "… would reach past ±1048576 px, the farthest a transform places pixels".

Extra memory per result pixel and time, 100 MP 8-bit layer, release build, M4 Max:

| | main | this PR |
|---|---|---|
| scale 110 % | 16.4 B, 0.8 s | 4.8 B, 0.6 s |
| rotate 15° | 12.5 B, 0.8 s | 3.4 B, 0.5 s |
| 90 % + 15°, Bilinear | 12.7 B, 0.5 s | 3.4 B, 0.3 s |
| 90 % + 15°, Bicubic | 19.9 B, 1.0 s | 12.4 B, 0.8 s |

The report's case (90 % and 15°, a 37708 x 35259 px 8-bit result) is refused on main; with this it takes 10.7 s and 6.1 GB on top of the 4.3 GB layer.

## Testing

- `a_gigapixel_layer_transforms_within_memory_usage`: the report's result fits the default at 8 bits, is refused at 16 bits with the message above, and fits with Memory Usage doubled.
- `memory_usage_is_what_a_transform_may_take` (integration test, real budget): refused at 1 MB, applied at 2 MB; fails on main.
- `a_result_past_the_warps_reach_is_refused_not_clipped`: a 2,000,016 px strip from x = 0 and a small layer moved 1.1M px are refused, the document untouched; the strip centred fits. Fails with the check off (the move then succeeds and leaves the layer empty). `output_clipped_matches_the_clamped_bounds` ties the check to the clamp.
- The #3773 and #6430 budget tests now use the byte budget; huge scales are still refused before anything is built.
- Engine unit tests run against 2²⁰ px of the widest format (32-bit CMYK with alpha, 20 MB), so every result the old 2²⁰ px test limit allowed still fits at any depth.
- algo, engine and ui-egui, merged into current main: 5881 tests pass; clippy `-D warnings`, wasm check, rustfmt, `xtask layers`, `scorecard --check` and `panic_hunt` clean.

## Not covered

- At 32 bits a pixel takes 16 bytes, so the default allows a smaller result than the old cap (537 MP rather than 1074 MP); the old cap let a 32-bit result alone take 16 GiB.
- A Bicubic downscale still makes a reduced copy of the source first (Photoshop's widened Bicubic); that copy isn't priced, and it is allocated infallibly, as on main. Everything the result itself needs is allocated fallibly.
- Puppet Warp keeps its own 2³⁰ px bound.
- No perf scenario covers Free Transform (P23 is not measurable), so `cargo xtask perf --quick` doesn't exercise this; the numbers above come from a throwaway harness.
