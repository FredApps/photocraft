Fixes #7491.

**What users saw:** a Vanishing Point perspective clone stroke made about three heap allocations per sampled pixel (4.6 million for one 40-dab stroke on a 24 MP image).

**Cause:** `sample` in `crates/algo/src/vanishing.rs` read its 2×2 bilinear footprint with `read_region` (output `Vec` plus a decoded default-pixel `Vec`) and `collect`ed the result into a new `Vec`, once per covered pixel of every dab.

**Change:** `sample` writes into caller-owned scratch. `clone_stroke` reads each dab's source footprint once into a reused buffer (`read_region_into`); a footprint outside it is read with one `read_region_into` into the same reused corner buffer (one tile lookup instead of four `read_pixel` calls). The window is skipped when it is more than 4× the dab's destination area (cloning from near to far in strong perspective), where decoding it would cost more than it saves. Output is byte-identical to `main`.

Why not just `read_pixel` for the four corners, as the issue suggests: I measured it, and it removed the allocations but was ~15% *slower* than `main`, because each corner is a separate `BTreeMap` tile lookup.

While rewriting the corner reads, `x0 + 2` became `saturating_add(1)` for the far corners: a source near `i32::MAX` panicked with "attempt to add with overflow" in debug builds. This is the same class as #918 (fixed for the destination footprint); I found no open issue for this line.

**Benchmark** (release, Apple Silicon, RGBA8 6000×4000, one 40-dab stroke of 300 px; harness kept out of the repo because the counting allocator needs `unsafe`):

| | `main` | this PR |
|---|---|---|
| heap allocations | 4,621,154 | 404 |
| time | 100–125 ms | 46–53 ms |
| whole-image checksum | identical | identical |

Near-to-far cloning toward the horizon, where the window is skipped (8000×6000, 200 dabs at v = 0.03 cloned from v = 0.97, 41 runs, median):

| dab size | `main` | this PR |
|---|---|---|
| 30 px | 0.32 ms | 0.29 ms |
| 60 px | 0.98 ms | 0.81 ms |
| 120 px | 4.30 ms | 3.43 ms |

In that regime each sample still makes one allocation (`read_region_into` decodes the default pixel), against three on `main`.

**Tests:**
- `sample_at_the_edge_of_i32_does_not_overflow`: fails on `main` ("attempt to add with overflow").
- `sample_interpolates_across_tile_edges`: a footprint straddling a tile edge, read from the surface, from a window holding it, and from a window holding half of it; four different corners in four tiles (both axes of the corner order); plus the default pixel outside every tile.
- Byte-for-byte comparison against the old `clone_stroke` (not committed) on RGBA8/16/32F, Gray8/GrayA8/Gray32F, CMYKA8, CMYK32F and Lab16A, on a torn-off plane, near the horizon and with NaN/inf/out-of-plane points: identical.
