## What changed

Inside a Flatpak, a second launch now hands its files to the running PhotoCraft over a Unix socket instead of a loopback port. #3755's hand-off binds `127.0.0.1` and records the port in `instance.json`; every `flatpak run` gets its own network namespace, so the second sandbox's loopback never reaches the first and the launch fell back to a separate window, as the PR noted. `$XDG_RUNTIME_DIR/app/<app id>/` is the same directory in every sandbox of the app and the user's alone (0700), so the primary listens on `instance.sock` there (0600) when `FLATPAK_ID` and `XDG_RUNTIME_DIR` are set, and writes `"socket"` instead of `"port"` to `instance.json`. Everything else is unchanged: the `instance.lock` election, the 256-bit token checked first and in constant time, the client cap, the request deadline, the `ok`-only-once-taken reply and the retry loop. A socket file left by a crashed primary is unlinked under the lock before binding; the primary removes its socket on shutdown. Outside Flatpak, and on Windows, nothing changes.

- `apps/photocraft/src/single_instance.rs`: `Transport` (`Loopback` | `Socket(path)`), chosen by `transport()`; `Endpoint` in `instance.json`; `Listener` and `Stream` over the two socket kinds; `claim_in` takes the transport so tests can pick it.
- `docs/development.md`: the "One instance per user" paragraph describes the sandbox case and drops the "needs its own follow-up" note.

## Evidence

The built binary run twice with the sandbox's environment (`FLATPAK_ID=ai.storyteller.photocraft XDG_RUNTIME_DIR=/run/user/1000`), the second with another file while the first is open:

```
$ cat ~/.config/photocraft/instance.json
{"pid":175734,"socket":"/run/user/1000/app/ai.storyteller.photocraft/instance.sock","token":"…"}
$ ls -l /run/user/1000/app/ai.storyteller.photocraft/instance.sock
srw------- 1 diego diego 0 Oct 18 23:48 /run/user/1000/app/ai.storyteller.photocraft/instance.sock
$ photocraft ~/Pictures/photocraft-test/blue.png
INFO  [main] photocraft: handed 1 file(s) to the running PhotoCraft
exit=0 after 0.85 s
```

The file opened as a tab in the first window. On the real Flatpak (0.10.0, `--share=network` not granted) the same second launch opens a separate window, which is the report in #1540; with `flatpak override --user --share=network` it hands over through loopback, which confirms the namespace as the cause. That `$XDG_RUNTIME_DIR/app/ai.storyteller.photocraft` exists inside the sandbox was checked with `flatpak run --command=sh`.

In two real sandboxes (this head built in release, packaged with `package.sh --formats tar` and the bundle manifest, installed as branch `test`, network not shared: `flatpak override --show` read `shared=!network`):

```
$ flatpak run ai.storyteller.photocraft//test            # first terminal: one window
$ ls -l /run/user/1000/app/ai.storyteller.photocraft/instance.sock
srw------- 1 diego diego 0 Oct 19 17:58 /run/user/1000/app/ai.storyteller.photocraft/instance.sock
$ flatpak run ai.storyteller.photocraft//test ~/Pictures/photocraft-test/blue.png   # second terminal
INFO  [main] photocraft: handed 1 file(s) to the running PhotoCraft
exit=0 after 0.19 s
$ wmctrl -l | grep PhotoCraft
0x09e00004  0 diego-Nitro-ANV15-51 blue.png — PhotoCraft      # still one window, the file is a tab
```

Closing the window removes `instance.sock` within a second and leaves no `photocraft` process; a third `flatpak run` becomes a new primary with a fresh socket, and closing it removes that one too.

## How it was tested

- New tests in `single_instance.rs`: `a_sandboxed_second_launch_hands_its_paths_over_a_unix_socket` (socket mode 0600, `instance.json` carries `socket` and no `port`, the second launch is forwarded, a wrong token is refused, shutdown removes the socket), `a_crashed_primary_s_socket_file_does_not_block_the_next_one`, and `the_socket_transport_needs_a_flatpak_id_and_a_runtime_directory`. The existing loopback tests are unchanged apart from reading the endpoint type.
- `cargo test -p photocraft --bin photocraft single_instance --locked` (14 tests), `cargo clippy -p photocraft --all-targets --locked -- -D warnings`, `cargo fmt --all -- --check`.
- End to end with the built binary and `FLATPAK_ID`/`XDG_RUNTIME_DIR` set as the sandbox sets them: see Evidence.

## Risk and rollback

Low: the socket transport is taken only when `FLATPAK_ID` is set, and a bind failure there falls through to the standalone launch exactly as before. Revert the single commit to roll back.
