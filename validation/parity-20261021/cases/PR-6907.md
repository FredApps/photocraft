## Cause

Not a hover or hit-test bug in the toolbar. The tool buttons are plain `Sense::click()` widgets, and egui hit-tests a press at the press position, so a click needs no hover before it. The report's other symptom, a blank band along the window's top and left edges, matches #2246: on some Windows 10 systems the compositor kept the undecorated window's caption and border, so the UI was drawn offset from where the pointer reported. A click then landed on the wrong spot. Hovering seemed to help because the hover highlight showed where the pointer really was, so the reporter could move until it sat on the intended icon. #2401, the fix for #2246, landed after 0.6.0 and shipped in 0.7.0.

## Fix

Nothing to change on main. This PR adds a regression test so that a toolbar click never comes to depend on a prior hover.

## Tests

- `panels::tests::a_click_without_a_prior_hover_picks_the_tool` sends only a primary press and release at the Brush and Type buttons, with no `PointerMoved` before them (the pointer has never entered the window), and checks that the tool becomes active.

The real-window offset fix (#2401) can't be tested headlessly; the reporter has been asked to retest on 0.9.0.
