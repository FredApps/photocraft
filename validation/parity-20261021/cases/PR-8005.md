## What the logs show

The reporter attached two debug logs (0.10.0, MSI build, Windows 11, RTX 4060 laptop). Both have a single silent gap of about 8 to 9 minutes on the main thread, starting right after launch. The first line after each gap is wgpu/naga building the canvas shaders for the newly opened document, and the whole naga burst takes well under a second. So naga is not what stalls. It is just the first thing that logs once the stall is over.

In both logs the stall ends about 7.5 to 9 minutes after launch, however long the user waited before opening. That matches the installed-font scan that `type_tool::warm_fonts` starts on a background thread at launch:

- The background open's worker decodes the file and finishes in a few milliseconds.
- `jobs_ui::after_open` then calls `file_open::with_missing_fonts` on the UI thread, which calls `type_extra_cmds::missing_fonts`.
- `missing_fonts` locked `photocraft_text::shared()` before it looked at the layers. The first `shared()` call blocks until the font scan finishes. That happened even for a JPG with no type layers.
- The open card had last painted 2% (or 95%), so the window sat there "Not responding" until the scan finished. Later opens are fast because the scan is done by then, and it starts over on the next launch. That is exactly what was reported.

PSDs with type also stall at 95% but stay responsive, because `io::text_import` waits on `shared()` on the worker.

## Change

- `type_extra_cmds::missing_fonts` returns at once for a document without type layers and never touches the shared text engine. This fixes the reported case: any JPG/PNG/etc. on the first open after launch.
- New `type_extra_cmds::has_type_layers`. When the opened document has type layers, `Session::start_open`'s worker waits for the shared engine itself (progress reads "Loading fonts"). The UI-thread missing-font check that follows then finds the engine ready and no longer freezes the window.
- Regression test `a_document_without_type_never_waits_for_the_text_engine`: it holds the shared engine locked and checks that `missing_font_warnings` still answers for a document without type. Before this change it blocked on the lock.

## Not addressed here

Why the font scan takes about 8 minutes on this machine is still unknown. The logs don't cover it: `FontDb::load_system_fonts` logs nothing, and it may come down to a very large font folder or slow per-file mapping on Windows. Until that is found, Type tool font menus show "Loading fonts…" for that long, and a document with type waits on its worker. The window stays responsive in both cases. A follow-up should time the scan and log the file count.
