## Cause
Photoshop 2026's Light adjustment layer is stored under the Brightness/Contrast `brit` key, with a `CgEd` descriptor holding more settings. `adjust_map::parse_any` read any `brit` + `CgEd` as Brightness/Contrast (only `Brgh`/`Cntr`), so Exposure, Highlights, Whites and Blacks were dropped with no warning (https://github.com/storytold/photocraft/blob/58f855a40f67a9b6a7e9168ea03c261226845705/crates/io/src/adjust_map.rs#L207-L218).

## Fix
- `adjust_map::is_extended_brit`: if a `brit` layer's `CgEd` has keys outside the Brightness/Contrast set (`Vrsn Brgh Cntr means "Lab " useLegacy Auto presetKind presetFileName`), it now stays `Adjustment::Unsupported`. The PSD writer then keeps its `brit` and `CgEd` blocks byte for byte while the layer is unchanged.
- The import warns about the layer by name: "its Light settings could not be read (Light adjustments ... aren't supported yet); the layer is kept as saved but has no effect".

## Tests
`psd_export::tests::light_adjustment_is_kept_verbatim_and_warned`: a synthetic Light-style `brit` + `CgEd` layer goes through export, import (with the warning) and re-export, and both blocks come back byte-identical. A plain Brightness/Contrast `CgEd` is still read as Brightness/Contrast. The existing `adjust_map` tests and clippy pass.

## Not in this PR
- The Light adjustment itself (#6543). Until then the layer has no visible effect (warned).
- Detection rests on the `CgEd` having extra keys. I had no real Photoshop 2026 file, so the test descriptor's extra key names are placeholders. Someone with `largetest.psb` should confirm that the layer's `CgEd` holds the Light values (and not a separate block), then map its real keys for #6543. The corpus suite was not run.
