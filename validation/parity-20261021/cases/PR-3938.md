## Summary

`packaging/windows/sign.ps1` downloaded `Microsoft.Trusted.Signing.Client` from the unversioned NuGet URL and loaded its dlib into `signtool`, next to the Azure signing secrets, with no version or integrity check (#2936, finding 1 of #1372). Once #3794 passes the Azure secrets to the release workflow, this branch is what PhotoCraft's own Windows releases will run.

The script now downloads a pinned version (1.0.95) and checks its SHA-256 before extracting it. On a mismatch it throws and never runs `signtool`. Upgrading the client is now a deliberate change to both values, and the comment above them says how to make it.

## No change to what gets signed today

- The unversioned URL resolves to 1.0.95 today (it redirects to `microsoft.trusted.signing.client.1.0.95.nupkg`). I downloaded it and the versioned URL, and the two files are byte-identical: SHA-256 `3bfcf1e0a3cb42af1692f0a8ed45c15de070c2de86f28a59b2795d904d8a920f`.
- NuGet's catalog entry for 1.0.95 lists the same SHA-512 and size (14,651,525 bytes).
- The package's `.signature.p7s` names Microsoft Corporation as the author signer, countersigned by the NuGet.org repository. I decoded it but did not validate the certificate chain.
- nuget.org keeps the existing signatures on published packages when it rotates its repository certificate ([NuGet blog, March 2024](https://devblogs.microsoft.com/nuget/the-nuget-org-repository-signing-certificate-will-be-updated-as-soon-as-april-8th-2024/)), so the pinned bytes shouldn't change underneath us.

## Testing

`sign.ps1` has no automated test and real signing needs the release secrets. I ran the Azure branch on Windows 11 under PowerShell 7.6 (the release workflow's `pwsh`) with dummy `AZURE_*` values and `SIGNTOOL` pointing at a stub. The stub logs its arguments and exits 1, the way signtool fails on dummy credentials.

- **Pinned version, expected hash:** the script downloads 1.0.95, the hash matches, and it passes `client\bin\x64\Azure.CodeSigning.Dlib.dll` to `signtool sign … /dlib … /dmdf …`. It then stops with "signtool sign failed with exit code 1", as expected with dummy credentials.
- **Expected hash altered by one byte:** the script stops with `Microsoft.Trusted.Signing.Client 1.0.95 has SHA-256 3BFC…920F, expected 00FC…920F: refusing to load it`. `signtool` is never called.
- The temporary `photocraft-sign-*` folder is removed in both runs.
- The packaging-lint PowerShell step (`Parser::ParseFile` on `packaging/windows/*.ps1`, then `check-icons.ps1`) passes locally.

No Rust code changes.

## Note for a follow-up

Every version of `Microsoft.Trusted.Signing.Client` is now unlisted on NuGet. Microsoft renamed Trusted Signing to Artifact Signing and asks existing customers to update their client tools ([Artifact Signing](https://azure.microsoft.com/products/artifact-signing)). The successor package is [`Microsoft.ArtifactSigning.Client`](https://www.nuget.org/packages/microsoft.artifactsigning.client).

This PR keeps today's package and only pins it. Moving to the successor changes the signing toolchain, so it belongs in its own change that can be tested against the real Azure account. The same pin applies to it.
