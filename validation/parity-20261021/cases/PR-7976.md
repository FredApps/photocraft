Found while testing `crates/engine/src/file_cmds.rs:690 (xml_unescape), used by li_values, find_attr and read_file_info` (no existing issue): File Info does not decode numeric character references in XMP text, so it shows `&#xA;` and `&#169;` literally.

## Cause
File Info did not decode numeric character references in XMP text, so it showed `&#xA;` and `&#169;` literally. `xml_unescape` only handled the five named XML entities, so the raw references stayed in Description, Title and the other fields. Saving an edited field then ran `xml_escape` over them, which turned `&#xA;` into `&amp;#xA;` and corrupted the stored text.

## Fix
`xml_unescape` now makes a single pass and decodes decimal and hex numeric character references along with the five named entities. A single pass means `&amp;#38;` decodes to `&#38;` and not `&`. Malformed or unknown references are left as they are.

## Not changed
`xml_escape` and the write path are unchanged. The decoding fix is enough because the read side no longer returns raw references to be re-escaped.
