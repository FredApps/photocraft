## What was wrong

The window can lose its own wgpu device, for example through a driver reset after the PC slept, or the OS killing a submission. After that, egui-wgpu can't draw another frame, and PhotoCraft never handled it. Depending on which egui-wgpu path meets the dead device first, the user gets one of two failures:

- **A crash.** A frame with shapes panics inside egui-wgpu (`renderer.rs:984`, "Failed to create staging buffer for index data"). The app exits with code 101 and unsaved work is lost (#1215). I reproduced this on an RX 6900 XT, on both Vulkan and DX12, by destroying the device in a running app.
- **A freeze that X can't close.** Frames that can't be presented are dropped ("Dropped frame with error: Validation"), so the window freezes. The close button then opens the unsaved-changes prompt, which the dead window can't draw. That's #3438's "unresponsive, and X won't close it". I reproduced it by keeping the frames empty after the loss: the app kept running, and `ui.inspect` showed the `discard` prompt open for `file.exit`.

Why the existing handling and tests missed it:
- The device-loss handling from #243 moves only the *document canvas* to the CPU.
- `ui.gpu.simulateLoss` only marks the health flag, so no test ever ran a frame on a really lost device.

## Change

- **`photocraft-gpu`:**
  - `DeviceHealth::device_lost()`: true only when wgpu itself reports the device lost (its callback, or a panicking poll), unlike a recorded fault.
  - `DeviceHealth::probe()`: a non-blocking poll that keeps running after a recorded fault.
- **`photocraft-format`:** `RecoveryStore::flush()` finishes queued autosaves and waits for them.
- **`photocraft-ui-egui`:**
  - The app keeps the window's device and its health flag: the GPU canvas's, or one from `watch_window_device` for the CPU canvas.
  - `gpu_status::check_window` runs at the end of every frame and probes the device. Once the device is lost, the frame draws nothing (the egui graphics are cleared), so egui-wgpu has nothing to upload.
  - The first time it sees the loss, it queues every unsaved document for crash recovery (whatever the autosave timer says), waits for the writes via `Services::flush_autosaves`, and closes the app without the prompt. The next launch reopens the documents ("Recovered …").
  - `ui.gpu.simulateLoss {destroy: true}` destroys the real device, so this path can be driven from the control channel.
- **`photocraft` (app):**
  - `flush_autosaves` is backed by `RecoveryStore::flush`.
  - The CPU-canvas path now watches the window's device instead of discarding its health flag.
- **Docs:** `docs/development.md` (device loss) and `docs/control-protocol.md`.

## Tests

- **`gpu_device_loss::a_lost_window_device_saves_unsaved_work_for_recovery_and_closes`** (ui-egui; runs on any adapter, WARP and llvmpipe included):
  - It runs the real eframe frame loop, makes a document dirty, destroys the device, then uploads the last frame through egui-wgpu's `Renderer::update_buffers`.
  - **Without the frame clearing, it panics with #1215's message and fails** (`left: (141, false)`).
  - With it, there's nothing to upload, the document was autosaved and flushed exactly once, and the app is closing.
- **`device_loss::only_wgpu_reports_a_real_device_loss`** (gpu).
- **`autosave::flush_writes_every_queued_autosave_before_returning`** (format).

Not verified:
- **A real sleep/resume on this machine.** Whether a driver reports a loss on resume depends on the driver.
- **The timing of a real loss.** On a real driver loss, wgpu calls the lost callback immediately (`lose()`). `destroy()` instead waits for the queue to empty, which is why the test waits for the device to go idle.

## For review

- **The app closes on its own after a loss.** Alternatives would be a native message box first (PhotoCraft has none today), or having the app restart itself, which needs care with `--control` ports. I'm happy to add either.
- **The recovery save ignores the Autosave preference.** `recover_on_launch` still decides whether the next launch reopens the documents.
- **`probe` adds one non-blocking `device.poll` per frame.**
