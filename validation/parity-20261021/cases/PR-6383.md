Fixes #688.

Windows releases ship no PDBs, so a profile of the installed PhotoCraft (WPA, Superluminal) shows addresses instead of function names, and a PDB from a local rebuild of the same commit doesn't match the published exes. The release build already writes `photocraft.pdb` and `photocraft_cli.pdb` (the exes record them by bare file name), they just weren't packaged.

## Change
- `packaging/windows/package.ps1`: after the portable zip, copies both PDBs from the release build into `photocraft-<v>-windows-<arch>-symbols.zip` in `dist/release`, plus `symbols.txt`. It fails the packaging step if a PDB is missing rather than shipping a partial zip. Signing doesn't change the PDB signature an exe records, so the PDBs match the signed exes. The shared release workflow (`craft-common-actions` `release.yml` → `draft-release`) uploads everything in `dist/release` and adds it to `SHA256SUMS.txt`, so no workflow change is needed.
- `packaging/windows/symbols.txt` (new): which binaries they match, and how to load them (copy next to the exe, or add the folder in WPA / Superluminal / Visual Studio / `_NT_SYMBOL_PATH`).
- `docs/releasing.md`: the asset table and a short "Symbols zip" note.

The release profile has `debug = 0`, so these PDBs carry function names but no source line tables. That is what function-level flame graphs need. Line tables (`CARGO_PROFILE_RELEASE_DEBUG=line-tables-only` for the Windows build) could follow if maintainers want them; I left the build settings alone. The PDB from my local release build is about 9.8 MB (2.3 MB zipped). macOS dSYMs and Linux debug files would be follow-ups in their own packaging scripts.
