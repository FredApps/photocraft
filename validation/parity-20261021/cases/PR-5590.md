### Problem

Committing Edit › Transform › Warp ran on the UI thread, with no progress and no cancel. On an 8000 × 6000 layer the window froze for 6.9 s (Arc) and 9.3 s (Flag).

Timing the steps of a Flag warp showed where that time goes. The mesh warp itself (`warp_triangles`) took 1.3 s. Writing its tiles took 0.5 s (since #6800, each worker encodes its own tiles). Then two serial whole-layer passes in `warp_layer` took most of the rest:

- `surf.convert(…)` re-encoded every tile into the format the layer already had: **2.0 s**.
- `composite_over` blended the warp over the cleared layer in float buffers: **2.3 s**. When the warp box holds the whole layer, there is nothing under it to blend.

My claim comment said the mesh warp was 7–9× slower per pixel than Free Transform's. That was wrong for Flag: most of that time was these two steps.

### Change

- **`warp_cmds`:** `edit.transform.warp` (and `layer.smartObjects.warp`, which shares `apply`) runs its edit through `edit_job`, as Free Transform does since #4218. In the desktop app, a commit is a background job with progress, and Esc cancels it without touching the layer. Scripts, tests and the web build run inline as before.
  - `warp_layer` takes the job's `Interrupt`. It checks it between the steps that don't check it themselves.
  - A layer that already has alpha is cloned (its tiles are shared) instead of converted.
  - When clearing the warp box leaves the layer empty, the warp is the result, without `composite_over`. A test checks this gives the old path's pixels: exactly at 8 and 16 bits, and within one float ulp at 32 bits, where the old blend's `t·a / a` rounded a few values.
- **`algo::warp`:** `warp_mesh_surface_with` reports progress per destination tile and skips the remaining tiles once cancelled, like `warp_surface_with` (#4218). `warp_mesh_surface` and `warp_triangles` keep their signatures.
- **`transform_tool`:** Undo or Redo while a Warp commit runs now says "Warp is still being applied", instead of naming Free Transform. Nothing else in the UI needed changing: #4218's commit path already handles a pending job from either command, keeps the session's preview on screen and ends it when the job does.

Not in this PR: the mesh warp's own per-pixel speed. That's most of Arc's remaining 4.2 s, and it can now be cancelled. I'd look at it separately.

### Measured

8000 × 6000 RGBA8 layer filled with a pattern, engine level (`Session::execute` inline, `Session::start` for the job). Intel Core Ultra 7 255H (16 threads):

| | `main` | This PR |
|---|---:|---:|
| Flag, inline | 9.3 s | **1.4 s** |
| Arc, inline | 6.9 s | **4.2 s** |
| UI thread blocked by a commit (job) | the whole warp | **0.2–1.1 ms** |
| Worker gone after cancel, 0.3 s / 1.5 s in | (no cancel) | Arc 31 / 66 ms, Flag 21 / 285 ms |

The 285 ms case is a cancel during the final write of the tiles, which doesn't check.

### Tests

- `algo`: `the_interruptible_mesh_warp_reports_progress_and_stops_when_cancelled`. Same pixels as `warp_mesh_surface`, progress above 0.9, and `None` when cancelled.
- `engine`:
  - `warp_runs_as_a_job_with_the_inline_result`: label "Warp", one undo step, same pixels as inline.
  - `a_cancelled_warp_leaves_the_document_unchanged`: the snapshot is not replaced, no undo step.
  - `a_warp_box_holding_the_whole_layer_gives_what_compositing_over_the_cleared_layer_did`: at 8, 16 and 32 bits.
  - `a_cancelled_warp_stops_in_a_selected_linked_mask`: a fill layer with a linked mask and a selection, warped with a cancelled interrupt, returns `Cancelled` (it ran to completion before the fix).
- `ui-egui`:
  - `a_warp_commit_runs_in_the_background_and_keeps_its_preview`: the job is labelled Warp, the session stays open with Undo refused, then it ends in one "Warp" step.
  - `esc_cancels_a_background_warp_commit`: the layer's pixels are untouched and there's no undo step.
