Fixes #7481

### Problem
After a shortcut that includes Alt (Ctrl+Alt+I for Image Size, or a custom Ctrl+Alt+E for Expand), releasing Alt put the keyboard on the menu bar with File lit, as a lone Alt tap does. The dialog the shortcut opened then didn't get Enter: Enter opened the File menu instead of confirming.

`menu_keys::Keys::keys` tells a lone Alt tap from Alt used in a chord: any key, text or click while Alt is held cancels the tap. It read the frame's `InputState::events`. The shortcuts run before the menu bar each frame and consume their key from those events (`consume_key`). So the bar never saw the I of Ctrl+Alt+I, and the Alt release counted as a tap.

### Solution
`crates/ui-egui/src/menu_keys.rs`: the tap is now judged on `InputState::raw.events`, every event the frame received, including keys another handler consumed. Which mnemonic or menu key the bar acts on still comes from the unconsumed `events`, so it still won't act on a key a shortcut already took.

A lone Alt tap still puts the keyboard on the bar, and Alt+letter still opens that menu.

### Tests
`menu_keys::harness_tests::alt_held_through_a_shortcut_does_not_put_the_keyboard_on_the_bar` drives the whole app (shortcuts, dialogs and the menu bar), not only the bar. It fails before this change, where the bar took the keyboard.
- Alt down, then Ctrl+Alt+I, then Alt up: Image Size is open and the bar did not take the keyboard.
- Enter then confirms Image Size and opens no menu.
- A lone Alt tap still focuses the bar.

cargo test -p photocraft-ui-egui --lib shortcut     # 99 passed
cargo test -p photocraft-ui-egui --lib menu_nav     # 23 passed

cargo fmt --all -- --check                         # clean

Checked in the running app on Windows with real key events (`keybd_event`: Ctrl down, Alt down, I down/up, Alt up, Ctrl up): Image Size opens, the menu bar stays unfocused, and Enter confirms the dialog.
