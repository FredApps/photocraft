## Pinned upstream reproduction and regression specification

The following is source material from the approved PR, not a record of testing this combined build. Test the stated scenario, values and regression names in addition to the procedure above.

Part of #6729 (the stuck middle-button drag).



The title bar's drag gap (`panels::title_bar`) and the overlay that keeps the gap draggable while a modal is open (`titlebar::modal_drag_overlay`) sent `ViewportCommand::StartDrag` on `drag_started()`, which is true for a drag with any mouse button. winit's `drag_window()` expects the left button to be down, so a middle-button drag on the gap (here from an AutoHotkey window-snap script) started a native move in a state the OS doesn't expect and the window got stuck.



Both now check `drag_started_by(PointerButton::Primary)`, the same check the edge resize zones (`resize_zones`) and the Linux caption-button drag (`caption_buttons`) in `titlebar.rs` already use. A left drag and a double-click on the gap work as before; a middle or right drag on the gap does nothing.



Not in this PR: the issue's second point, returning `HTCAPTION` from `WM_NCHITTEST` for the gap so external window tools see it as a native caption. That is a Windows-only window-procedure change, and the triage comment asks for it as its own ticket.



Test: `middle_button_drag_in_the_gap_does_not_start_a_window_drag` (`crates/ui-egui/src/titlebar.rs`) does a middle-button drag on the gap and checks that no `StartDrag` is sent, then an ordinary left drag, which sends one, then a middle drag again with a modal open (over the overlay). Without the fix the middle drags send `StartDrag`. The test helper `gesture_by` takes the button; the existing helpers still use the primary button.
