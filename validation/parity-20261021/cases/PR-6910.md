Fixes #2095.

## Cause
In the browser, eframe 0.36.2 turns one finger or pen tap into **two** primary presses and two releases: one pair from Pointer Events (`pointerdown` / `pointerup`, which fire for touch and pen too) and one from Touch Events (`touchstart` / `touchend`), which mobile browsers fire for the same contact. `pointerdown` runs a frame of its own, so the `touchstart` press lands in the next frame while the button is still held. The menu bar titles (`menus.rs` `title_press`) and press menus (`press_menu.rs`) toggle on the press, so the twin press closed the menu the first one had just opened. Desktop Chrome with a mouse sends no Touch Events, which is why it works there.

## Fix
New `photocraft_ui_egui::touch_twins::drop_twins`, called from the web shell's `raw_input_hook`: it drops a primary press that arrives while the button is already held (pressed within 0.5 s) and a primary release that arrives while it is already up. A press held longer still passes, so a release the browser never sent can't lock the pointer down. Desktop builds are unchanged.

## Tests
- `touch_twins::tests::a_tap_opens_a_menu_title_every_time`: drives the real menu bar with the event sequence eframe produces for a tap. Without the hook the tap leaves File closed (the bug); with it, tap opens, tap closes, tap opens again.
- `touch_twins::tests::a_press_held_for_long_still_passes`: twin press and extra releases are dropped; a stale press is kept.

Not tried on a real Android device. The report also mentions a DeX mouse; a mouse sends no Touch Events, so that case isn't explained by this and may need a follow-up if it persists.
