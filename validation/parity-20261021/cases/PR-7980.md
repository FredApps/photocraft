## Pinned upstream reproduction and regression specification

Part of #211 (P32, brush release on a long stroke).



P32 ("brush release: 600-point stroke, 200 px soft, 24 MP") went from 0.31–0.36 ms to 7.5–8.1 ms p50 (p95 up to 22 ms, over its 16 ms budget) between 2d2e4993 (10-14) and main 46e538b3, reproduced on Linux (fork A/B, ubuntu-latest, 3 interleaved rounds). The canvas refresh in that row is of an empty rect, so the time is in the engine: an engine-only copy of the row puts it in the `paint.stroke` commit (0.17 → 3.93 ms min), not in offering the live stroke.



Bisecting that bench on the fork (first-parent, 2d2e4993..46e538b3) lands on 286ff735 (#3847): the commit takes 0.13 ms min at its parent 3e428e73 and 2.97 ms at 286ff735. Since then, `Session::edit` reports `step_damage(before, after)` for every edit. For the released stroke that asks for the painted layer's content bounds, which scans every tile the stroke touched (each is new, so the per-tile cache in `compose::bounds` misses). `Tile::content_bounds` compared each row pixel by pixel against the default pixel, so the mostly untouched rows of a soft stroke's tiles cost a slice compare per pixel.



## What



`Tile::content_bounds` compares each row against one row of the default pixel in 64-byte blocks: an untouched row is a few block compares, and a row with content is narrowed to the first and last differing byte inside the first and last differing block. A pixel differs exactly when one of its bytes does, so those bytes' pixels are the first and last differing pixels and the bounds are the same. Every caller (`Surface::content_bounds`, the cached `compose::bounds::content_bounds` the GPU planner and the CPU compositor use, `step_damage`) gets the same result, faster.

## Tests



`tile_content_bounds_match_a_per_pixel_scan`: one differing byte at every byte position of a pixel, at and around the 64-byte block boundaries and the row ends, in pixel sizes 1, 2, 3, 4, 6, 8 and 16 bytes, checked against a per-pixel scan; plus a pixel differing in every byte. The existing `tile_content_bounds_scans_against_the_given_pixel` and `content_bounds_and_prune` still apply.
